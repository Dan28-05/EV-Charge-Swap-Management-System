# Architecture and Technology Roadmap

Last updated: 2026-11-23

This document records the intended architecture and the approved use of portfolio technologies. Technology is introduced to solve a concrete problem, not to increase the tool count.

## 1. Architectural baseline

- ASP.NET Core REST API organized as a modular monolith.
- Angular client with Customer, Operator, and Admin experiences.
- PostgreSQL is the transactional source of truth.
- EF Core Code First migrations define schema history.
- ASP.NET Core Identity, JWT access tokens, and hashed rotating refresh tokens provide authentication.
- Customer email/phone verification uses expiring one-use codes stored durably in PostgreSQL. Phone numbers are normalized to Vietnamese E.164 format for version one. Refresh-token rotation preserves the original 30-day session deadline.
- Development uses an in-memory code inbox. Production delivery routes email through Resend and SMS through Twilio with secrets supplied by environment configuration. Vietnamese SMS uses a pre-registered alphanumeric Sender ID and approved transactional OTP template. Provider failure returns a temporary-unavailable response and removes the unsent challenge so retry is possible.
- Password recovery reuses the durable verification challenge and delivery adapter with a separate `reset` purpose. Recovery is limited to verified channels; five-minute codes permit at most five failed attempts. Identity validates the new password, its security stamp invalidates issued access tokens, and active refresh tokens are revoked in the same database transaction.
- Physical state is confirmed by Operators. Scheduled jobs only handle time-based transitions.
- Public API contracts and schema changes require tests and review.
- Swagger UI in Development renders the OpenAPI document generated by ASP.NET Core.

Target topology:

```text
Angular
   ↓
ASP.NET Core modular monolith
   ├── PostgreSQL               source of truth
   ├── Redis                    cache and distributed rate limits
   └── Transactional Outbox
           ↓
        RabbitMQ
        ├── Notification Worker
        ├── Search Indexer Worker
        └── Reporting Worker
                 ↓
           Elasticsearch

API and workers
   ↓ OpenTelemetry/OTLP
Aspire Dashboard locally; production-compatible observability backend later
```

Do not split the API into microservices merely to use infrastructure. A separate Worker process is introduced when message consumption exists.

## 2. Redis decisions

Approved use cases:

- Cache public Location details and popular read queries.
- Distributed rate limiting for login, reservation, and sensitive endpoints when multiple API instances exist.
- Optional short-lived cache of account security state when database validation becomes a measured bottleneck.
- OTP or verification codes with TTL when that feature is implemented.
- Optional per-access-token denylist when immediate, per-session access-token logout becomes a requirement.

Guardrails:

- Redis is not the source of truth.
- Redis availability never decides whether a charging bay or battery can be reserved.
- Reservation creation always rechecks PostgreSQL inside a transaction protected by constraints.
- Cache failure must fall back to PostgreSQL where safe.
- Refresh-token history remains durable in PostgreSQL.

Redis is not required for the current login implementation. Introduce it only with one of the approved use cases and corresponding failure tests.

## 3. RabbitMQ and reliable messaging

RabbitMQ is the selected first message broker. Do not add Kafka in parallel without a distinct streaming requirement.

Candidate integration events:

- `ReservationCreated`
- `ReservationCancelled`
- `ReservationExpired`
- `CustomerCheckedIn`
- `ReservationCompleted`
- `ChargingSessionCompleted`
- `BatterySwapCompleted`
- `InvoiceCreated`
- `PaymentSucceeded`
- `IncidentReported`
- `LocationUpdated`

Required reliability patterns:

1. Write the business change and `OutboxMessage` in the same PostgreSQL transaction.
2. A background publisher reads unprocessed Outbox rows and publishes to RabbitMQ.
3. Use durable queues, persistent messages, publisher confirms, and explicit consumer acknowledgements.
4. Assume at-least-once delivery. Consumers must be idempotent.
5. Record processed message IDs in an Inbox/consumer table when the side effect is not naturally idempotent.
6. Use bounded retry for transient errors and a dead-letter queue for poison messages.
7. Expose outbox backlog, retry, and DLQ metrics.

The reservation realtime consumer handles committed reservation events through the Outbox. The authenticated notification hub sends the reservation ID only to the owning customer, while the public station hub publishes current availability. Clients read the authorized reservation API after an event or reconnect and keep periodic reconciliation as a fallback.

Operators currently assigned to the station receive a private dashboard refresh signal. Public map subscriptions are bounded and return an availability snapshot when the connection is restored.

The notification consumer stores Operator inbox items for new holds, incidents affecting a visit, and successful QR payments. It selects current station assignees whose assignment had begun when the event occurred, and uses a deterministic notification ID per event and recipient. SignalR tells the dashboard to refresh the inbox after the notification is saved.

For a new hold, the API sends the station refresh signal immediately after the transaction commits. The Outbox remains available for delayed delivery, and duplicate refresh signals are safe because clients read current state.

Failure demonstration required for the portfolio:

```text
RabbitMQ is unavailable
→ business transaction still commits with an Outbox row
→ RabbitMQ returns
→ publisher sends the pending event
→ consumer processes it once logically
```

## 4. Thiết kế Elasticsearch

Elasticsearch phục vụ các chức năng tìm trạm sau đây.

- Tìm kiếm toàn văn theo tên và địa chỉ trạm.
- Gợi ý kết quả khi người dùng đang nhập.
- Lọc theo dịch vụ và giá.
- Lập chỉ mục tọa độ bằng kiểu `geo_point` để tìm theo khoảng cách hoặc bán kính.
- Sắp xếp kết quả theo khoảng cách.
- Xếp hạng kết quả độc lập với các bảng giao dịch.

Luồng đồng bộ chỉ mục

```text
Thông tin trạm thay đổi trong PostgreSQL
→ Ghi sự kiện LocationUpdated vào Outbox
→ RabbitMQ
→ Tiến trình cập nhật chỉ mục
→ Chỉ mục Elasticsearch
```

Các nguyên tắc triển khai

- PostgreSQL là nguồn dữ liệu chính.
- Kết quả tìm kiếm có thể chậm hơn dữ liệu vừa ghi và sẽ đồng nhất sau khi đồng bộ.
- Đặt chỗ và thanh toán dựa vào PostgreSQL.
- Có quy trình tạo lại toàn bộ chỉ mục từ PostgreSQL và có thể chạy lại khi cần.
- Tiến trình cập nhật dùng ID trạm làm ID tài liệu. Xử lý lại cùng một sự kiện cho ra cùng kết quả.

Milestone tìm trạm dùng endpoint `GET /api/locations/search` với tên và địa chỉ, hỗ trợ tiền tố và bỏ dấu tiếng Việt. Elasticsearch trả ID theo thứ tự phù hợp. API đọc PostgreSQL theo các ID đó để kiểm tra lại quyền hiển thị công khai và lấy số tài nguyên hiện tại. Truy vấn theo bán kính tiếp tục qua API nearby. Bộ lọc giá và tìm theo khoảng cách bằng Elasticsearch thuộc phần mở rộng.

Consumer chạy trong worker RabbitMQ của ứng dụng. Ghi tài liệu và dựng lại chỉ mục được tuần tự hóa bằng một advisory lock PostgreSQL dành riêng cho chỉ mục. Sự kiện tồn đọng sau khi Elasticsearch gián đoạn được thử lại có giới hạn trước khi chuyển vào DLQ. Rebuild nạp chỉ mục mới rồi chuyển alias nguyên tử. Khi không truy cập được chỉ mục, việc tìm kiếm tiếp tục qua PostgreSQL.

## 5. Observability

Use OpenTelemetry for correlated logs, distributed traces, and metrics across HTTP requests, PostgreSQL, Redis, RabbitMQ, Elasticsearch, and workers.

Minimum telemetry:

- HTTP request duration and error rate.
- PostgreSQL query and transaction duration.
- Redis hit/miss and fallback counts.
- Outbox backlog and oldest-message age.
- RabbitMQ publish, consume, retry, and DLQ counts.
- Elasticsearch indexing/search latency and failures.
- Business metrics for reservations, sessions, swaps, payments, and incidents.

Propagate trace context through message headers so an API request can be correlated with background consumers. Use the standalone Aspire Dashboard locally through OTLP; choose a production backend later without changing application instrumentation.

Current implementation details:

- `Serilog.AspNetCore` handles structured logging across HTTP requests and background workers.
- `OpenTelemetry` instruments ASP.NET Core, `HttpClient`, Npgsql (`Npgsql.OpenTelemetry`), and custom RabbitMQ publish/consume `ActivitySource` spans with W3C `traceparent` / `tracestate` header propagation. OTLP export activates automatically when `OTEL_EXPORTER_OTLP_ENDPOINT` is configured.
- SignalR supports multi-instance scale-out via `Microsoft.AspNetCore.SignalR.StackExchangeRedis`, enabled explicitly via `SignalR:UseRedisBackplane=true` when Redis is configured.
- `ForwardedHeaders` honors explicit `ForwardedHeaders:KnownProxies` and `ForwardedHeaders:KnownNetworks` allow-lists rather than trusting arbitrary upstream proxies.
- Non-Development environments require `LocationSearch:ApiKey` whenever `LocationSearch:Endpoint` is configured.
- Frontend Docker deployment runs non-root `nginxinc/nginx-unprivileged` on port `8080` (bound to `127.0.0.1:4200:8080` in local Compose) with strict CSP and security headers in `frontend/nginx-security-headers.conf`.

## 6. Delivery order

### Customer Station Finder milestone

The public Angular route `/` uses Leaflet with OpenStreetMap attribution. It consumes the existing paged `GET /api/locations` and `GET /api/locations/{id}` contracts without changing the API or schema. The page owns selection and pagination; list and map components share the same deduplicated set of loaded locations. Each load adds 20 locations. Directions open Google Maps with destination coordinates.

The finder uses browser geolocation and the nearby API for browsing around the map. A separate paged PostgreSQL-backed API searches station names and addresses across the network; the UI no longer exposes a radius selector. Price, booking and personal history remain later milestones. Only fields returned by the API are presented. No messaging or search infrastructure is needed for this page.

Location operating status is a manually updated, public field (`Unknown`, `Open`, `Closed`, `Maintenance`) stored in PostgreSQL. Visibility stays separate: hidden locations are omitted from public endpoints, while publicly visible closed or maintained locations remain discoverable. Service hours and per-resource availability are separate future data; no automatic status transition is inferred from time or hardware.

### Phase 1 — Core resources

1. Admin Location CRUD.
2. `ChargingBay` with equipment and parking state.
3. `Battery` lifecycle.
4. `ServiceHours`.
5. `OperatorAssignment` and location-scoped authorization. Admin provisions resources and sets the initial schedule. Operators edit service hours and update charging bay and battery states at assigned locations.
   Each Operator has at most one current location. PostgreSQL enforces this with a partial unique index; historical assignments remain available after transfer.
   Operator resource changes record the acting user and time. Public availability is calculated from resources and holds in PostgreSQL; the prior manually entered Location counts are legacy data.

### Phase 2 — Reservations and operations

1. Fifteen-minute holds for a specific resource.
2. Database-enforced concurrency and one-active-reservation-per-customer rule.
   Reservation creation also supports customer-scoped idempotency keys. Reservation status changes write the audit record and Outbox event in the same database transaction. PostgreSQL checks that a bay belongs to the reservation's station and that a battery belongs to that station while its reservation is active.
3. Idempotent expiry job.
4. Check-in, charging session, vehicle departure, and no-charge flow.
   The backend records Operator-confirmed vehicle arrival separately from check-in, permits one meter-backed charging session per reservation, and holds the bay until departure is confirmed. Customer and Operator UI for this flow is pending.
5. Battery swap and inspection/charging lifecycle.

### Phase 3 — Reliable asynchronous processing

1. Outbox schema and publisher.
2. RabbitMQ topology.
3. Notification Worker.
4. Idempotent consumers, retry, and DLQ.

Charging bay and battery faults create an [incident report](incident-report-erd.md) with an Outbox event in the equipment update transaction. The Operator fault command reassigns or cancels an affected unused reservation under the same station lock used by booking and charging. Customer inbox notifications are created for fault cancellations. Reassignments publish a reservation refresh. Incident changes, audit records and resolution events commit together.

### Phase 4 — Redis

1. Location read cache with explicit invalidation and fallback.
2. Distributed rate limiting.
3. Cache metrics and outage tests.

### Giai đoạn 5 — Elasticsearch

1. Định nghĩa các trường và kiểu dữ liệu trong chỉ mục trạm.
2. Xây dựng tiến trình cập nhật chỉ mục từ sự kiện RabbitMQ.
3. Bổ sung API tìm kiếm toàn văn, gợi ý khi nhập, lọc và tìm theo khoảng cách.
4. Kiểm thử việc tạo lại toàn bộ chỉ mục và kiểm tra kết quả tìm kiếm đồng nhất sau khi đồng bộ.

### Phase 6 — Billing and observability completion

1. Tariffs, immutable applied prices, invoices, and payments.
   Operators publish effective-dated tariffs at their assigned station. Charging snapshots the tariff at start and retains the demo rate as a fallback at stations without a charging tariff. Swap snapshots the tariff at handover and requires a configured rate. Migration `HardenIndexesAndBillingConstraints` widens VND currency rates to `numeric(14,2)`, adds non-negative invoice amount check constraints, and indexes hot reservation/invoice/outbox queries. See the [service billing ERD](swap-billing-payment-erd.md).
2. Verified idempotent payment webhooks.
   Development mock callbacks use HMAC-SHA256 and persist the provider event ID alongside the payment and invoice update. PostgreSQL serializes each invoice's attempts and allows one successful payment per invoice.
3. OpenTelemetry traces and business/infrastructure metrics.
4. Demonstrable failure and recovery scenarios.

#### V1 counter checkout

- Create the invoice and its Outbox event in the same PostgreSQL transaction as service completion. Return the persisted invoice in the completion response. During the transition, handle already queued completion events idempotently and review completed legacy services that still lack invoices.
- Use the existing payment model and invoice serialization for cash and QR. Enforce one successful payment per invoice in PostgreSQL. Store a nullable `CollectedByOperatorId` foreign key for new cash receipts and preserve legacy payment records. Persist the pay-later approval and UTC due time. Check for any pending invoice for the customer in the PostgreSQL reservation-creation transaction, after resolving any idempotent replay.
- Pin the QR reference to [EMV QRCPS Merchant-Presented Mode v1.1, 27 November 2020](https://www.emvco.com/documents-search/?post_id=12643&type=specifications) for the dynamic payload structure. Use [NAPAS's VietQR announcement](https://napas.com.vn/napas-va-cac-ngan-hang-chinh-thuc-ra-mat-thuong-hieu-vietqr-va-dich-vu-chuyen-tien-nhanh-napas247-bang-ma-qr-182755.htm) for the Vietnam profile reference, which cites the State Bank's Decision 1928/QĐ-NHNN. The Development mock uses test-only recipient data, VND, the full invoice amount, a unique attempt reference and a valid payload checksum. Acceptance uses a decoder and a signed mock webhook, without bank routing or a claim of bank interoperability.
- Commit the successful payment, invoice change and `PaymentSucceeded` Outbox event together. After commit, SignalR sends a refresh signal only to the owning customer and Operators currently assigned to the invoice's station. Reuse Outbox delivery for recovery. The clients reread authorized invoice state after a signal or reconnect and render the green check from the saved status.

## 7. Portfolio quality bar

The implementation must be explainable through failure behavior:

- Two concurrent reservation requests cannot both succeed.
- RabbitMQ downtime does not lose a committed business event.
- Duplicate messages do not duplicate side effects.
- Redis downtime degrades performance rather than correctness.
- Elasticsearch can be rebuilt from PostgreSQL.
- Trace IDs connect API requests, Outbox publishing, and Worker consumption.

Avoid adding both RabbitMQ and Kafka, premature microservices, Kubernetes before multiple deployable processes exist, or infrastructure without tests and observable failure behavior.
